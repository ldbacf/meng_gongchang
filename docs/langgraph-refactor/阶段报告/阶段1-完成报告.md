## 六、关键设计决策（实现要点）

1. **`src/db.py` 纯转发层 + 惰性代理**：`engine`/`async_session` 变代理对象（`__call__`/`begin`/`__getattr__` 转发到容器），30+ 处 `from src.db import async_session` 调用点零改动；engine 由容器创建、close 统一 dispose。代理内部延迟 import deps 打破循环。
2. **额度三阶段**：`KeyManager.acquire` 返回 `Reservation(token_id, reservation_id, pages)`，reserve 即 INCR 占额；`commit` 仅确认状态、`refund` DECR 退回。调用点（main/admin/scan_submit）改为 `acquire → submit → commit/refund`。明文 token 仅经 `TokenVault.resolve()` 进 MinerU 请求；Redis 全程只存 token_id。
3. **token_id 持久化**：DocumentTask 无 token 列（不动 Alembic）→ worker claim 后写 Redis `batch:{batch_id}→token_id`（TTL 7 天），`retry_document` 优先读映射、回退 `vault.first_id()`。
4. **ES mapping 同源**：`es_mappings.py` 定义 26 字段完整 mapping（`dynamic:strict` + ik_smart，与 init_es 逐字一致）+ `GENERIC_KB_EXTRA_MAPPING`（`title` + `metadata` object，子字段 text+ik_smart 以满足 search 的 match 语义）。在线自动建合并后创建。
5. **队列可见性超时 = 1800s** > 单批最坏时长（MAX_POLL_TIME 1200s + 索引余量），防误回收；XAUTOCLAIM 每轮迭代回收孤儿 pending，worker 处理完才 ack。
6. **事件总线订阅模型**：每进程每 kb 一个 pubsub 订阅 + 引用计数（首个连接 subscribe、归零 unsubscribe），`ws_manager.broadcast` 保留签名改 publish，`broadcast_doc_update`/doc_deleted 全走总线。

## 七、大白话拆解 & 改动↔业务场景对应

> 本节用通俗比喻解释每个核心改动，并说明它对应**哪条业务**、带来什么收益。

### 7.1 消灭“全局单例”→ 建立“总控室”（AppContainer）
- **以前**：每个文件想用数据库、ES、MinIO，就自己 `import` 一个全局变量。就像每个房间都自己拉了一根电线，乱且危险。
- **现在**：所有电线、水管都接到 `AppContainer`（总控室）。谁想用电，必须通过总控室的开关（`get_xx()` getter）获取，统一管理电源开关（`start/close`），测试时还能换“假电线”（fake）避免触电。

### 7.2 队列升级：从“排队叫号”变成“挂号 + 回执”（Redis Streams）
- **以前**：用 Redis List 做任务队列，像饭馆门口排队，服务员喊一个走一个；万一服务员忘了（Worker 崩溃），这个人就丢了。
- **现在**：Redis Streams 相当于每个任务发一张“挂号单”，处理完要“签字确认”（ACK）；处理人中途晕倒（崩溃），系统超时后“自动重派”（XAUTOCLAIM），任务绝不丢失（At-least-once）。

### 7.3 额度记账：从“脑子记”变成“账本记”（Redis 原子记账）
- **以前**：MinerU token 的当日额度存在进程内存，像收银员凭脑子记，一重启就全忘。
- **现在**：额度记在 Redis，每次扣减用 Lua 脚本精确计算，不会多扣少扣；流程改为“预占→确认→退还”（先冻结额度，提交成功才扣、失败退回），跨进程一致。

### 7.4 模型配置：从“各家自定”变成“标准图纸”（Schema 双轨合一）
- **以前**：Elasticsearch 和 Milvus 的“建表图纸”各写一套，经常不一致，导致数据写不进/查不到。
- **现在**：图纸统一放在 `es_mappings.py` / `milvus/schema.py`，两边照着同一张图施工，字段完全对应。

### 7.5 事件广播：从“对讲机”变成“广播站”（Redis Pub/Sub）
- **以前**：后台处理完文件直接调用本进程的 WebSocket 通知前端；多台服务器（多进程）下会“喊不到人”。
- **现在**：后台只管对“喇叭”（topic）喊“文件更新了！”，所有前端（订阅者）都能收到并刷新，实现跨进程通信。

### 7.6 改动 ↔ 业务场景对应表

| 技术改动 | 对应的业务场景 | 业务收益 | 验收用例 |
| --- | --- | --- | --- |
| AppContainer 收敛全局单例 | 上传/解析/检索问答全部模块的外部客户端获取 | 统一启停、测试可注入 fake、不泄漏连接 | A-1.4 |
| Redis List → Streams 队列 | PDF 解析任务队列（MinerU 提交 → Worker 轮询） | Worker 崩溃不丢批、多 worker 不重复处理 | A-1.3 |
| 额度内存态 → Redis 原子记账 | MinerU 多 Key 每日页数配额管控（`MINERU_MAX_PAGES_PER_KEY`=1000 页/key） | 跨进程一致、重启保留、预占→扣/退 | A-1.2 |
| ES/Milvus schema 双轨合一 | 文档入库索引管线（chunk → ES + Milvus） | 线上建索引与 init 脚本一致，写入/检索不漂移 | T-1.3 / T-1.4 |
| ws 单例 → Redis 事件总线 | 前端文档管理后台的实时状态刷新（WS 推送） | 多进程下前端跨进程实时收到解析/索引进度 | A-1.6 |
| Milvus 幂等 upsert | 文档重索引 / 图重跑 | 重复入库不撞主键 | A-1.5 |
| MinerU 结构化异常 | Worker 解析错误分类 | 致命（token 失效）判失败 / 可重试（网络抖动）继续 | T-1.11 |
