## 1. 背景与动机

MedRAG 目前是一个功能完整的医疗文献 RAG 问答系统，端到端管线已跑通（PDF 上传 → MinerU 解析 → 三粒度切分 → ES BM25 + Milvus 双路索引 → 意图识别 → 双路召回 → RRF 融合 → Rerank → LLM 流式回答）。但随着功能演进，后端 `backend/src/` 积累为 **26 个扁平模块**，存在以下结构性矛盾：

1. **无分层架构**：接口层、应用逻辑、领域逻辑、基础设施全部平铺，`main.py`（718 行）与 `routers/chat.py`（491 行）成为 god 文件，业务管线硬编码在路由里。
2. **管线不可编排、不可观测、不可续跑**：入库管线是 worker 隐式 while 轮询 + 字符串匹配错误分类；问答管线是 `chat_stream` 内联串行六步。两者都无状态机、无断点、无重试，失败静默降级。
3. **数据契约漂移**：ES mapping 双轨、Milvus schema 双轨、doc_id 口径两套、删除 key 错位导致残留，`chunk_id`/`doc_id` 在线与离线路径不一致。
4. **基础设施耦合**：模块级可变全局单例（ES/Milvus/Embedding/KeyManager/Redis/MinIO），无依赖注入、无生命周期管理、无健康检查；额度为进程内内存态。
5. **可测试性为零**：无 pytest、无 CI，`test/` 是依赖真实外部服务的手工冒烟脚本。

**重构抓手**：以 **LangGraph** 作为应用层流程引擎，把入库与问答两条管线显式建模为有状态图；以 **四层架构**（接口 / 应用 / 领域 / 基础设施）+ **端口适配器** 重组代码，实现低耦合高内聚、可单测、可观测、可断点续跑。

## 2. 重构目标与成功标准

### 2.1 目标

| 编号 | 目标                                                                         | 度量方式                                                                             |
| ---- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| G1   | 分层清晰、依赖单向：`interface → application → domain ← infrastructure` | 静态检查：禁止反向 import；`domain` 仅依赖 stdlib                                  |
| G2   | 入库与问答两条管线图化，节点化、可观测、可断点续跑                           | 崩溃后从 checkpoint 恢复；每节点有耗时/状态事件                                      |
| G3   | 消除所有模块级可变全局单例，统一由 DI 容器管理生命周期                       | `grep` 无 `_ES_CLIENT/_MILVUS_CONNECTED/_EMBED_MODEL/_manager` 模块级 `global` |
| G4   | 数据契约单一真相源：ES mapping / Milvus schema / doc_id / chunk / 状态机     | 在线自动建与规范脚本同源；删除无残留                                                 |
| G5   | 队列与额度 at-least-once、跨进程一致、崩溃不丢                               | kill worker 后批任务可恢复；多进程额度一致                                           |
| G6   | 建立可回归的测试安全网                                                       | pytest + pytest-asyncio + testcontainers 接入 CI，全量自动化验收               |
| G7   | 保留 wire 协议兼容：SSE / WS / pipeline_steps / 前端契约                     | 旧前端无需改代码即可消费升级后的 SSE（v 信封向后兼容）                               |

### 2.2 成功标准（全局退出条件）

- 全部验收用例通过（见 §11 全局验收总纲）。
- 全量回归：上传→解析→切分→索引→检索→回答全链路在新架构下跑通，行为与旧版等价或更优。
- 崩溃注入测试通过：入库/回答过程中 kill 进程，重启后从最后完成节点续跑，无重复脏数据。
- 删除测试通过：删除文档后 ES / Milvus 无残留 chunk。
- `grep` 全部 `zhong_guo_quan_ke` 魔法串替换为 `KBKind` 策略；`scripts/` 收敛为瘦 CLI 复用同一服务。

## 3. 非目标（明确不做）

| 项                                    | 说明                                                                                                |
| ------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 不做前端大重构                        | 前端仅做协议兼容适配（SSE v 信封、error/heartbeat 分支、openapi-typescript 生成类型），不改交互骨架 |
| 不更换检索算法                        | ES BM25 + Milvus 双路 + RRF + Rerank 的召回/融合/精排语义保留，不引入新检索器                       |
| 不更换解析引擎                        | MinerU v4 API 协议与 429 退避保留，不切换解析供应商                                                 |
| 不做分布式微服务拆分                  | worker 独立进程/容器，但系统整体仍是单体应用 + 独立 worker，不引入服务网格                          |
| 不重构 chunker 的切分算法本身         | FullMdParser 状态机与 L0/L1/L2 切分规则原样保留（高价值资产），只做归位与单测保护                   |
| 不做离线大数据迁移平台                | 存量数据迁移作为一次性工作项执行，不建常驻迁移服务                                         |
| 不引入 LangGraph Server / Studio 依赖 | 图在应用进程内执行，不依赖 LangGraph 平台部署                                                       |

## 4. 现状多角度分析

> 以下为对现状五个子系统的分析结论（2026-08-07 逐文件评审得出，由多角度分析 agent 与 LangGraph 技术实测共同核验）。

### 4.1 文档解析与任务管线（上传 → MinerU → 队列 → Worker → 入库触发）

**职责**：上传收单与 md5 去重秒传、多 Key 额度分配与轮换、按 token 分组批提交 MinerU、Redis List 队列、Worker 轮询批状态、下载解包存 MinIO、触发索引、pipeline_steps 步骤进度、retry。

**核心问题**：

| 级别  | 问题                                                                                                       | 影响                                                                |
| ----- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 🔴 高 | 状态机隐式：`status` 是 `String(32)` 无约束字符串，`status` 与 `pipeline_steps` 各自独立写入可漂移 | 重试判断依赖 steps 而非 status，二者不一致导致重复提交/错误重试路径 |
| 🔴 高 | 队列无 ack：`BRPOP` 出队即删，worker 崩溃即丢批，任务永久停在 PROCESSING                                 | at-most-once；多 worker 并发消费无可见性超时/死信/重投              |
| 🔴 高 | 额度预占不退回：`acquire` 后立即 `release`（实为扣额），批提交失败仍烧额度                             | 失败重试浪费配额，真实用量被高估                                    |
| 🔴 高 | 额度内存态：进程内单例、每日惰性重置，重启清零                                                             | 多进程部署额度互相覆盖，单日超用                                    |
| 🔴 高 | 致命错误靠字符串匹配（"找不到任务"…），文案变化即漏判                                                     | 不可恢复任务反复轮询到超时                                          |
| 🔴 高 | 索引在 worker 内同步串行 +`deepcopy steps_ref` 跨线程回写                                                | 索引崩溃恢复差；Milvus insert 无幂等，重跑撞主键                    |
| 🔴 高 | worker 与 API 进程耦合：lifespan 内嵌`run_worker_background`，另有一套独立 `run_worker()` 入口         | `--workers 4` 时每进程各起一个 worker；跨进程广播丢失             |
| 🟡 中 | 上传两套实现（main`_submit_batches` vs admin `_submit_one_file`）                                      | 双入口行为漂移                                                      |
| 🟡 中 | retry-from-mineru 复用已消费 batch_id、取`key_mgr._tokens` 私有字段                                      | 重试不可靠、访问私有实现                                            |
| 🟡 中 | 轮询 1200s 超时直接 FAILED，MinerU 稍后完成被永久误标                                                      | 无补偿/对账                                                         |

### 4.2 切片 / 向量化 / 索引入库

**核心问题**：

| 级别  | 问题                                                                                                                                                                                                                                     | 影响                                                                     |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 🔴 高 | **两套切分实现**：在线走 `indexer.process_document` 内联重写，离线走 `scripts/run_chunker.py → chunk_document`。二者产出的 chunk 结构、chunk_id、doc_id 均不一致（在线 doc_id=完整 md5，离线 doc_id=article_id 兜底 md5[:8]） | 在线/离线结果不可比；重跑失去幂等；按 doc_id 删除互相不命中              |
| 🔴 高 | ES mapping 双轨：`init_es.py` 是完整 ik_smart `dynamic:strict` 30+ 字段；`es_bulk_write` 自动建只有 7 字段、standard 分词、无 IK                                                                                                   | 新 KB 索引无中文分词、字段漏映射，检索/过滤能力与预置索引不一致          |
| 🔴 高 | Milvus schema 双轨：`init_milvus.py` 10 字段含 level/doi/chunk_type；`milvus_insert` 自动建 4 字段                                                                                                                                   | 在线入库文档缺过滤字段，`_milvus_search` 被迫写两套 output_fields hack |
| 🔴 高 | 在线逐 chunk`embed_query` 单条编码，离线批量 `encode`                                                                                                                                                                                | 在线入库吞吐远低，bge-m3 利用率低                                        |
| 🔴 高 | **删除 key 错位**：`_cleanup_es_milvus` 取 `task_batch_id or md5`，在线文档 batch_id 是 MinerU batch UUID，而索引 doc_id 是 md5                                                                                                | 在线入库文档删除后 ES/Milvus 残留，越删越多                              |
| 🟡 中 | bge-m3 模型工厂三份 + search 又包一层                                                                                                                                                                                                    | 可能加载两份 bge-m3 常驻内存                                             |
| 🟡 中 | 维度 1024 / nlist 散落硬编码，自动建 nlist=1024 vs init nlist=128                                                                                                                                                                        | 换模型需改多处                                                           |
| 🟡 中 | `indexer` 依赖 `src.search._get_es/_connect_milvus` 私有函数                                                                                                                                                                         | 分层倒挂                                                                 |

### 4.3 在线 RAG 问答通路（意图 → 检索 → 融合 → 重排 → 回答 → 引用 → SSE）

**核心问题**：

| 级别  | 问题                                                                                                                              | 影响                                                |
| ----- | --------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| 🔴 高 | `chat.py` 单路由 490 行硬编码串行管线，`event_generator` 无 try/except，ES/Milvus 不可用时异常直接炸断流，无 `t:error` 事件 | 用户消息已落库但 AI 消息缺失；管线无法单测/复用     |
| 🔴 高 | 失败静默降级不透明：rerank 失败返回原序、intent 失败直通、answer 失败把`[错误:...]` 拼进正文落库                                | 错误被当正常内容持久化；无从定位降级                |
| 🟡 中 | rag_steps/SSE 指标字典三处×2 手写，易漂移；SSE 缺 error/heartbeat；RagStepSchema 形同虚设                                        | 观测不可信；长流被网关超时掐断                      |
| 🟡 中 | 全局单例无生命周期；`_milvus_search` 每次 `collection.load()`                                                                 | 外部抖动后持续失败；每次检索首屏慢                  |
| 🟡 中 | 多轮指代消解脆弱：窗口硬编码、GENERIC_PROMPT 无指代指令、intent 失败则完全未处理                                                  | 通用 KB 多轮追问召回错误                            |
| 🟡 中 | `is_generic = kb.slug != "zhong_guo_quan_ke"` 魔法串穿透三层                                                                    | 新增 KB 行为不符；缺 kb_id 时静默落默认库成隐性 bug |
| 🟡 中 | 三处重复编排：`chat_stream` / `search_with_intent` / `search_and_answer`；`search_with_intent` 尾部有不可达代码           | 行为在三处漂移                                      |
| 🟢 低 | DB 会话与流时长耦合：generator 闭包持有 route 的 db session 贯穿整个流                                                            | 高并发连接池耗尽                                    |

### 4.4 接口层与前端消费

**核心问题**：

| 级别  | 问题                                                                                                                     | 影响                                          |
| ----- | ------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------- |
| 🔴 高 | SSE 生成器内联整个 RAG 管线，接口层与业务逻辑零分离                                                                      | 无法单测/复用，改召回策略必须改端点           |
| 🔴 高 | AI 消息流结束后一次性落库，中途 abort/断网/报错即整条丢失（用户消息成孤儿）                                              | 数据一致性差，无断点续跑                      |
| 🔴 高 | 鉴权边界不一致：`/api/v1/documents*` 与 `/tokens/usage` 无鉴权（泄露 MinerU 额度）；WS token 放 query 串且不查黑名单 | 任意未登录者上传/查文档/探测额度              |
| 🟡 中 | SSE 协议四处手工镜像无版本号；前端 RagStep 只有 pending/completed，后端无 failed 态                                      | 协议一改四处同步；step 失败前端永远 pending   |
| 🟡 中 | 两套平行文档 API（main 无鉴权批量 vs admin 有鉴权单文件）                                                                | 行为与权限不一致                              |
| 🟡 中 | schema 与前端 types 手工镜像无 codegen                                                                                   | 前后端契约漂移                                |
| 🟡 中 | 遗留`/documents/{doc_id}/pdf` 预签名端点死代码；`_fetch_l0_meta` 硬编码 index='chunks'                               | 预签名 URL 绕过鉴权窗口；通用 KB PDF 回退失效 |

### 4.5 基础设施与数据模型

**核心问题**：

| 级别  | 问题                                                                                               | 影响                              |
| ----- | -------------------------------------------------------------------------------------------------- | --------------------------------- |
| 🔴 高 | schema 演进无方案：lifespan`create_all` + 手写 `ALTER TABLE ADD COLUMN IF NOT EXISTS`          | 多环境漂移；加列侵入启动路径      |
| 🔴 高 | 配置不可校验且双真相源：config.py 与 key_manager.py 各自`os.getenv` 解析                         | 拼错 key 静默取默认；弱口令默认值 |
| 🔴 高 | 全局单例无 dispose：engine/redis pool/milvus/bge-m3 不释放                                         | 连接泄漏；外部重启后 stale 连接   |
| 🔴 高 | 无 pytest/无 CI，`test/*.py` 依赖真实外部服务                                                    | 重构无安全网                      |
| 🟡 中 | 状态机仅应用层强制；worker 写`steps_ref[task.status.lower()]` 污染 JSONB 契约                    | 前端渲染多余步骤行                |
| 🟡 中 | DocumentTask 契约不稳定：`batch_id` 字段过载、md5 全局 unique 使一文只属一 KB、PDF 查找 3 套回退 | 多 KB 场景被模型限制              |
| 🟡 中 | `langgraph 1.2.1` 仅作传递依赖，src 零使用、无 DI                                                | 引入前需显式声明并补 DI           |

### 4.6 痛点汇总（重构动因排序）

按影响面与修复成本排序，重构优先解决：

1. **管线不可编排/不可续跑/不可观测**（入库 while 轮询、问答串行六步、失败静默）→ 由 LangGraph 图化解决。
2. **数据契约双轨漂移**（ES/Milvus/doc_id/删除 key）→ 由契约冻结 + 单一真相源解决。
3. **分层倒挂与全局单例** → 由四层架构 + DI 容器解决。
4. **可靠性缺口**（队列无 ack、额度内存态、崩溃丢批丢回答）→ 由 checkpoint + Redis 持久化解决。
5. **测试与观测缺失** → 由测试基建 + metrics/trace 解决。

## 5. 目标架构：四层 + 端口适配器

### 5.1 依赖模型

```
          ┌────────────────────────────────────────────┐
          │               interface 层                  │  路由薄壳 / SSE·WS 适配 / DTO / DI 装配
          └────────────────────┬───────────────────────┘
                               │ 调用用例（service / graph）
          ┌────────────────────▼───────────────────────┐
          │               application 层                │  用例编排 / LangGraph 图 / 独立 worker
          └────────────────────┬───────────────────────┘
                               │ 依赖 domain 端口与聚合
          ┌────────────────────▼───────────────────────┐
          │               domain 层                     │  纯函数 / 状态机 / 契约 / 端口抽象（零外部依赖）
          └────────────────────▲───────────────────────┘
                               │ 实现端口（适配器）
          ┌────────────────────┴───────────────────────┐
          │           infrastructure 层                 │  AppContainer / 适配器 / ORM / 迁移
          └────────────────────────────────────────────┘
```

依赖方向严格单向：`interface → application → domain ← infrastructure`。

**禁止规则**（架构红线，静态检查 enforce）：

| 规则                                                                                                                    | 说明                                                                                                   |
| ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| domain 零外部依赖                                                                                                       | 仅 stdlib/dataclasses/typing/enum；不得 import sqlalchemy/httpx/redis/pymilvus/elasticsearch/langchain |
| interface 不 import infrastructure 具体类                                                                               | 只能经`AppContainer` 取适配器                                                                        |
| 禁止 import`src.search._get_es/_connect_milvus`、`key_manager._tokens`、`llm._CHAT_MODEL/_EMBED_MODEL` 等私有全局 | 全部改端口/容器注入                                                                                    |
| 禁止`slug == "zhong_guo_quan_ke"` 魔法串                                                                              | 由`KBKind` 策略对象取代                                                                              |
| scripts 一律经 application service 或 infra 工厂                                                                        | 禁止`sys.path.insert` 直 import src 内层                                                             |

### 5.2 各层职责与关键模块

| 层                       | 职责                                                                                                                                                                                                                              | 关键模块                                                                                                                                                                              |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## 6. LangGraph 图设计

> 两个图的 Mermaid 可渲染图见 [`LangGraph双图设计.md`](LangGraph双图设计.md)（含 IngestionGraph、QAGraph、SSE 事件流映射）。

### 6.1 通用工程约束（实测结论，必须遵守）

以下约束来自 langgraph 1.2.1 环境的真实核验（2026-08-07）：

| #   | 约束                                    | 说明                                                                                                                                                                                                                                                                        |
| --- | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C1  | **显式声明依赖**                  | `pyproject.toml` 必须显式声明 `langgraph>=1.2,<2` 与 `langgraph-checkpoint-postgres`，不得依赖 langchain 传递；锁版本避弃用面                                                                                                                                         |
| C2  | **checkpoint DDL 入 Alembic**     | `AsyncPostgresSaver` 需要的 `checkpoints`/`checkpoint_blobs` 表必须由 Alembic 版本化迁移创建，不得依赖 `.setup()`                                                                                                                                                   |
| C3  | **compile 必须挂 checkpointer**   | `interrupt` 在未挂 checkpointer 时**静默不暂停**（实测直接放行）。图 compile 一律带持久 saver（测试路径带 InMemorySaver）——架构红线                                                                                                                               |
| C4  | **RetryPolicy 显式 retry_on**     | langgraph 默认`retry_on` 只重试 `ConnectionError` 与 HTTP 5xx，不会重试自定义 `Transient` 异常。节点级重试必须显式传 `retry_on=lambda e: isinstance(e, TransientXxx)`                                                                                               |
| C5  | **无原生 sleep**                  | poll 长轮询（≤1200s）不能做阻塞节点内`while`。用 `poll_count + MAX_POLL_TIME` 状态机走条件边（pending→暂停→scheduler 定时 resume），配 `RecursionLimit` 防自环失控                                                                                                 |
| C6  | **QAGraph 无"选择性 checkpoint"** | langgraph 每 superstep 自动落一次 checkpoint，不支持"只持久化到 rerank"。两种可接受方案：① 接受每节点落 Postgres（token 不进 state 控写入量）；② 拆两段独立 compile（检索段带 saver、answer 段 InMemorySaver），断线续跑=重放 answer 段                                   |
| C7  | **SSE 流式双通道**                | 节点级 step 事件走`stream_mode=['updates','values']`；token 走 `astream_events(version='v2')` + 节点内 `adispatch_custom_event('token', {...})` → 消费端 `on_custom_event`（已实测逐 token 到达）。心跳帧由独立 asyncio task 在 graph 运行期间定时写队列，不放图内 |
| C8  | **并发模型**                      | 首选`async` 图 + `sync` 阻塞节点（graph 自动线程池化），事件全程在事件循环流向 SSE；仅需精确控线程数时才用 `asyncio.to_thread` 包关键节点。禁止"整图丢 to_thread"                                                                                                     |
| C9  | **版本 API 面**                   | 统一从`langgraph.types` / `langgraph.checkpoint.base` 导入；`langgraph.graph.StateNode` 不可导入，`langgraph.pregel.*` 已弃用                                                                                                                                       |
| C10 | **子图线程**                      | 子图`thread_id` 建议继承父图命名空间，避免多 thread 干扰续跑                                                                                                                                                                                                              |

### 6.2 入库图 IngestionGraph（应用层，batch 级线程）

**目的**：替换 worker 隐式 while 轮询 + 字符串错误匹配 + deepcopy 闭包回写。图成为 `pipeline_steps` 与 `document_tasks.status` 的唯一写入方，checkpoint 提供断点续跑与按步重试（取代 admin retry 对 `PIPELINE_STEPS_ORDER` 的下标重置）。

**节点**：

```
submit①(enqueue，API 侧 document_service 完成 acquire-commit-refund + MinerU 批提交；图从批入队后开始)
   ↓
poll_parsed  ←─(pending: checkpoint 暂停 → scheduler TTL 唤醒回到自身, poll_count+1 ≤ MAX_POLL_TIME)
   ↓ done
download_assets → unpack_store → dispatch_index
                                        │ 逐 doc 启动/续跑 index_document 子图
                                        ↓
                              index_document 子图：
                              read_markdown → parse_md(FullMdParser) → chunk_document
                              → embed_batch(bge-m3 encode(list)) → es_write(bulk,_id=chunk_id)
                              → milvus_write(按 chunk_id 先删后插 upsert 幂等)
                                        ↓
finalize（全 READY→READY；任一 failed→FAILED + WS doc_update；写 pipeline_steps 终态）
```

**边/分支**：`poll_parsed`: `done→download_assets`；`pending→(暂停/scheduler 唤醒)`；`failed/timeout→fatal_or_retry` 条件边（retryable→requeue / 非 retryable→finalize FAILED）。子图任一步抛 `Transient`→节点级 `max_retries` 自环重试；抛 `Fatal`→短路 finalize。

**状态契约** `IngestState` 字段：`task_id, doc_id, md5, kb_id, kb_kind, es_index, milvus_collection, batch{batch_id,md5_list,token_id,submit_ts}, md5_to_item, pipeline_steps, parsed, chunks, vectors, es_write, milvus_write, poll_count, error{step,type,message}, fatal`。

**checkpoint**：`langgraph-checkpoint-postgres`；`thread_id=batch_id`（批图）与 `task_id`（子图）；每节点边界把 `pipeline_steps` 写库（图是唯一写入方）。

### 6.3 问答图 QAGraph（message 级线程）

**目的**：收敛 `chat.py` 490 行硬编码串行管线与 `search_with_intent/search_and_answer` 三处重复编排为单图；checkpoint 解决"用户消息已落库但 AI 消息丢失"痛点（中断从最后节点续跑）；失败节点级降级且 `metrics.degraded` 可观测。

**节点**：

```
build_context（历史窗口 回答10 turns/意图2 turns + KB 目标解析 + KBKind）
  → analyze_intent（Medical/Generic 策略，指代消解+重写；失败降级=原 query + degraded）
  → [条件边 USE_QUERY_EXPANSION] expand_query
  → embed_query + dual_recall（ES BM25 + Milvus COSINE，并行前驱）
  → rrf_fusion（k=20 按 chunk_id 去重 + ES 富字段回填）
  → rerank（Qwen3-Reranker；失败保序返回 + degraded，不静默）
  → build_citations（按 doc_id 去重取前 5，L0 回填 title_cn/journal，snippet 200 字）
  → generate_answer（DeepSeek 流式；token 经 on_token 回调泵入 asyncio.Queue → SSE t:text）
  → persist_message（落库 AI 消息 citations+rag_steps + 会话 updated_at；产 t:done 带 message_id）
  → END
任意节点异常 → error_handler（产 t:error{code,message,retryable} + 落库 failed 的 AI 消息）
```

**状态契约** `QaState` 字段：`message_id, conversation_id, user_id, query, kb{kb_id,es_index,milvus_collection,kb_kind,policy_ref}, history, rewritten_query, intent{name,confidence,coverage,degraded}, expanded_query, hits[SearchHit], reranked, citations, answer, rag_steps, stream_buffer, error{step,kind,message,retryable}, done`。

**checkpoint**：`thread_id=conversation_id:message_id`；token 级流式内容不进 state（只写节点边界），避免高频序列化。方案按 C6 选择：采用**方案①**（每节点落 Postgres，answer 不写 token），若写频成为瓶颈再升级**方案②**（拆两段 compile）。

**流式**：`stream_mode=['updates','values']` 产节点进出 `t:step`；`astream_events v2` + `adispatch_custom_event('token')` 产 `t:text`；`build_citations` 完成后产 `t:cite`；`persist_message` 产 `t:done`。心跳帧独立 task。

### 6.4 图状态与 DB 双写一致性

- 图状态是**节点间传递**的工作内存；DB 是**唯一持久真相**（document_tasks / messages / rag_steps / pipeline_steps）。
- 每节点结束（`on_after_node` 钩子，应用层自定义实现）把节点结果投影写 DB，保证"图状态与 DB 双写一致"。
- 断线/崩溃恢复：从 checkpoint 读回图状态，重跑剩余节点；`done` 帧携带 `message_id` 供前端幂等去重。

## 7. 数据契约

> 契约一旦冻结，不得静默变更。任何变更需走契约评审。

### 7.1 TaskStatus 状态机

- DB 层 `status` 列改 **SQL Enum/CHECK**：`pending, processing, parsed, indexing, ready, failed`（冻结值与前端 `types/knowledge.ts` 逐字一致）。
- 显式迁移表：`PENDING→PROCESSING`（提交成功）→`PARSED`（mineru done）→`INDEXING`（触发索引）→`READY | FAILED`；任一步可→`FAILED`（带 error）；`FAILED→PENDING`（重试）。非法迁移抛领域异常。
- 图是 `status` 与 `pipeline_steps` 的唯一写入方。

### 7.2 pipeline_steps

```python
StepState = {status: Literal['pending','running','done','failed','skipped'],
             ts: float, target_index: str|None, target_collection: str|None,
             count: int|None, error: str|None}
PipelineSteps = {upload, mineru, chunking, embedding, es_write, milvus: StepState}
# keys 固定 PIPELINE_STEPS_ORDER，禁止写非 pipeline key（停用 worker 写 task.status.lower()）
```

### 7.3 doc_id 统一口径

- **冻结**：`doc_id = meta.article_id 兜底 md5[:8]`，在线入库与预置文献导入同源。
- ES `_id = chunk_id`、Milvus 主键 `= chunk_id`（保证写节点幂等）。
- 删除 key 统一为 `doc_id`（修复 batch_id/md5 错位残留）。

### 7.4 chunk 结构契约定稿

- `chunk_id` 命名：`__L0 / __L1__{num}[_pN] / __L2__table_{tn}`。
- 字段：`chunk_id, doc_id, level, chunk_type, doi, journal, section, article_type, title_cn, heading_stack, heading_depth, refers_to_tables, content, html_body`（在线/离线共用 `chunk_document` 单入口）。
- content 前缀注入不变：`【标题】【摘要】【关键词】【章节】【作者结论】【表注】`。

### 7.5 SearchHit 契约（保留）

`chunk_id, doc_id, level, chunk_type, doi, journal, title_cn, title, section, article_type, heading_stack, content, html_body, score_rrf, score_rerank, score_milvus, score_es, rank_milvus, rank_es`（rank 哨兵 `999999`，四套分数）。

### 7.6 领域事件

`TaskSubmitted{task_id,md5,kb_id,batch_id,token_id,pages}`、`BatchEnqueued{batch_id,md5_list,token_id,ts}`、`ParseSucceeded{batch_id,md5_list,assets_dir}`、`ParseFailed{batch_id,md5_list,error_type:Fatal|Transient,message,retryable}`、`IndexStepCompleted{task_id,step,count}`、`DocReady{task_id,md5,doc_id,es_index,milvus_collection}`、`DocFailed{task_id,md5,error}`、`DocDeleted{doc_id,es_index,milvus_collection}`。

### 7.7 SSE 协议 v1（信封）

每帧带版本信封 `{"v":1, ...}`（向后兼容旧前端 useSSE，旧字段保留）：

| 帧              | 契约                                                |
| --------------- | --------------------------------------------------- |
| `t:step`      | `{v,k:intent                                        |
| `t:text`      | `{v, c: token}`                                   |
| `t:cite`      | `{v, citations:[{idx,doc_id,title,snippet,md5}]}` |
| `t:done`      | `{v, conversation_id, message_id}`                |
| `t:error`     | `{v, code, message, retryable}`（新增）           |
| `t:heartbeat` | `{v}`（新增）                                     |

metrics 由单一构建函数产出，消除三处×2 手写字典。

### 7.8 WS 协议（保留）

`{type: doc_update|doc_deleted, doc: DocumentResponse}` 按 kb_id 分组广播；订阅端断线后按 kb_id 拉快照恢复。

### 7.9 队列消息（Redis Streams）

`BatchMessage{batch_id, md5_list, token_id, submit_ts, attempts}` —— **token 明文改 token_id**（修复明文 token 落缓存）。

### 7.10 额度契约

`QuotaLedgerEntry{key_id, date, pages, action:reserve|commit|refund, ref:task_id}`；Redis key `quota:{key_id}:{date}` 原子 INCR/DECR。语义修正：`reserve`（预占）→ `commit`（仅 MinerU 提交成功扣额）→ `refund`（失败退回）。

## 8. 关键设计决策与取舍

| 决策           | 选择                                          | 取舍说明                                                                                           |
| -------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| LangGraph 定位 | 应用层流程引擎，不渗入 domain                 | 图编排用例，纯函数资产留 domain，避免为图而过度状态化                                              |
| 双图 vs 单图   | 入库图 + 问答图，各自独立线程与状态           | 生命周期/恢复粒度不同，拆开更清晰                                                                  |
| 队列           | Redis Streams + 消费者组（adapter 已落地、worker 已接通） | 相对 List 增复杂度，换 at-least-once 与多 worker 安全；BRPOPLPUSH 已评估为更简备选，但 claim/ack/DLQ 语义与 Streams 消费者组更匹配，直接采用 Streams |
| 额度持久化     | Redis 原子记账                                | 跨进程一致；修正"先扣后提交失败不退"                                                               |
| checkpoint     | PostgresSaver 主选                            | 本栈已有 PostgreSQL；Redis saver 仅在 QA 图写频瓶颈时作低延迟备选（需确认 AOF 持久化）             |
| domain 纯度    | domain 定义纯契约，ORM 落 infra               | 增加 mapper 样板，换 chunker/状态机/RRF 可单测                                                     |
| doc_id 口径    | 统一为 article_id 兜底 md5[:8]                | 破坏性变更，存量需重刷（一次性迁移）                                                        |
| SSE 演进       | 加 v 信封渐进演进                             | 旧前端无需同步重构；error 帧改变"永远 pending"现状，前端必须消费新分支                             |
| 秒传/查重      | KB 内查重，跨 KB 复制新 task 保留 parsed 引用 | 禁止 reassign kb_id 归属漂移                                                                       |

## 9. 技术风险与架构红线

### 9.1 红线（不可妥协）

1. **compile 必须挂 checkpointer**（C3）。
2. **RetryPolicy 显式 retry_on**（C4）——否则节点自环重试静默失效。
3. **domain 零外部依赖**；禁止跨层私有 import。
4. **图是 pipeline_steps/status 唯一写入方**；worker 停写非 pipeline key。
5. **Milvus 写入幂等**（按 chunk_id 先删后插/upsert），否则重跑撞主键。

### 9.2 主要风险

| 风险                                                                | 缓解                                                                       |
| ------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `langgraph-checkpoint-postgres` 未安装、表 DDL 未建 → 图不可续跑 | 显式声明依赖 + Alembic 建 checkpoint 表                             |
| 存量 ES/Milvus 数据 doc_id 口径与过滤字段缺失                       | 一次性重刷 + 迁移窗口双写，验收过滤字段非空、删除无残留             |
| worker 迁独立进程后 WS 跨进程广播丢失                               | EventBus（Redis Pub/Sub）+ API 侧按 kb_id 查询兜底恢复                     |
| SSE 断连时图是否继续执行                                            | 定义语义：图继续执行至 persist_node（不丢 AI 消息），done 帧支持延迟补投递 |
| 多 worker 消费与"在途批"并发双处理                                  | checkpoint + 队列可见性超时 + 禁止复用已消费 batch_id；补并发测试          |
| KB 级权限缺失（ChatSendRequest 无 kb 校验）                         | 加 KB 作用域授权依赖，拒绝用例进验收                              |
| 额度全部耗尽的上传拒绝路径未定义                                    | `document_service` 提交前前置校验，返回 `429/403 QUOTA_EXHAUSTED`      |
