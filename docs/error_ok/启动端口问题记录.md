# 启动问题记录（端口冲突 / Windows 保留端口段）

> 记录 2026-08-07 按 README 启动 MedRAG（后端 + 前端）时遇到的环境问题、根因与解决方案。
> 目录：`docs/error_ok/`

| 项 | 值 |
| --- | --- |
| 操作系统 | Windows 11 Pro 10.0.22631 |
| 后端 | FastAPI + uvicorn（Python 3.12.11，backend/.venv） |
| 前端 | Vite 8（Node v24.16.0 / npm 11.9.0） |

## 问题 1：后端 uvicorn 无法绑定 8000 端口（被 Attu 占用）

### 现象
`uv run uvicorn src.main:app --port 8000` 启动时，lifespan 已执行完（bge-m3 加载、桶初始化、Worker 启动均正常），但绑定端口报错并退出：

```
ERROR: [Errno 10048] error while attempting to bind on address ('0.0.0.0', 8000)
```

此时访问 `http://localhost:8000/health` 返回的是 **Attu 的 Next.js 404**（`/app/dist/build/index.html`），而非本项目的 FastAPI 响应。

### 根因
`backend/docker-compose.yml` 中 Attu（Milvus 管理面板）映射了 `8000:3000`：

```yaml
attu:
  ports:
    - "8000:3000"   # ← 宿主 8000 被 Attu 占用，与后端 API 8000 冲突
```

Docker 先于后端进程绑定了宿主 8000，uvicorn 无法再绑定同一端口。

### 解决
把 Attu 的宿主端口改为 8002（避开后端 8000），重建容器：

```diff
  attu:
    ports:
-     - "8000:3000"
+     - "8002:3000"
```

```bash
docker compose up -d attu     # Recreated
netstat -ano | grep ":8000"   # 确认 8000 已空闲
uv run medrag-api --host 0.0.0.0 --port 8000   # 启动成功（入口见「问题 3」，勿裸跑 uvicorn）
```

## 问题 2：前端 Vite 无法绑定 5173（Windows 保留端口段）

### 现象
`npm run dev` 报错：

```
Error: listen EACCES: permission denied ::1:5173
Error: listen EACCES: permission denied 127.0.0.1:5173
```

`netstat` 查 5173 **无任何进程占用**，但 IPv4/IPv6 绑定均被拒。

### 根因
Windows 为 Hyper-V / WinNAT 保留了动态端口段，`5172-5271` 在其内，**5173 恰好落入保留段**，因此 bind 返回 EACCES（非 EADDRINUSE，所以 netstat 查不到占用）：

```
netsh interface ipv4 show excludedportrange protocol=tcp
── 开始端口 5172  结束端口 5271   ← 包含 5173
```

### 解决
把 Vite dev 端口改为保留段之外的 5171：

```diff
  server: {
-   port: 5173,
+   port: 5171,   // 5173 落入 Windows 保留端口段(5172-5271)，无法绑定
```

```bash
npm run dev     # VITE ready，Local: http://localhost:5171/
curl http://localhost:5171/              → 200
curl http://localhost:5171/api/v1/auth/me → 401（代理已连通后端，鉴权生效）
```

## 附：测试脚本控制台 GBK 编码问题（次要）

运行 `test/test_query_intent.py` 时，脚本在打印 `⚠️ 提示`（emoji）处崩溃：

```
UnicodeEncodeError: 'gbk' codec can't encode character '⚠'
```

根因：Windows 控制台默认 GBK 编码无法编码 emoji。**不影响测试逻辑**（DeepSeek 意图识别已成功返回）。解决：显式指定 UTF-8 输出再运行：

```bash
PYTHONIOENCODING=utf-8 uv run python test/test_query_intent.py
```

## 问题 3：checkpointer 创建失败 —— uvicorn ≥0.36 用 loop_factory 绕过了 event loop policy

> 记录 2026-09-13。目录整理（`src/` → `app/`）后新增入口 `medrag-api` 时发现。

### 现象
用 `uv run medrag-api` 启动（**确实走的是带修正的入口**），日志仍报：

```
[API] embedding-service 就绪
[API] 警告: Postgres checkpointer 创建失败（图不可用）: Psycopg cannot use the
      'ProactorEventLoop' to run in async mode. ...
[API] 提示: Windows 下请用 `uv run medrag-api` 启动（会切到 SelectorEventLoop）...
```

即：**已经用了 `medrag-api`，提示却还在叫你去用 `medrag-api`**——提示本身是误导。

### 根因
uvicorn 版本是 **0.47.0**（`pyproject` 写 `>=0.34`，uv 解析到了 0.47）。**从 uvicorn 0.36 起
`Config.setup_event_loop()` 被移除**，`Server.run()` 改成：

```python
def run(self, sockets=None):
    return asyncio_run(self.serve(sockets=sockets), loop_factory=self.config.get_loop_factory())
```

关键：**`asyncio.run(coro, loop_factory=...)` 传了 loop_factory 就完全绕过 event loop policy**，
而 uvicorn 在 Windows 上把它硬编码为 Proactor：

```python
# uvicorn/loops/asyncio.py
def asyncio_loop_factory(use_subprocess: bool = False):
    if sys.platform == "win32" and not use_subprocess:
        return asyncio.ProactorEventLoop      # ← 无视 policy
    return asyncio.SelectorEventLoop
```

所以 `set_event_loop_policy(WindowsSelectorEventLoopPolicy())` 被静默忽略。

各 `loop=` 取值实测（`Config.get_loop_factory()`）：

| `loop=` | 返回 | 结果 |
| --- | --- | --- |
| `"auto"`（默认） | `ProactorEventLoop` | ❌ policy 被绕过 |
| `"asyncio"` | `ProactorEventLoop` | ❌ 同上 |
| **`"none"`** | **`None`** | ✅ 回落 policy → Selector 生效 |

### 解决
`app/run_api.py`：设 policy 之外，**给 uvicorn 传 `loop="none"`**：

```python
_configure_event_loop()          # 设 WindowsSelectorEventLoopPolicy
uvicorn.run("app.main:app", host=..., port=..., loop="none")   # ← loop_factory=None → 用 policy
```

并把 `container.start()` 里那句误导提示改成说明真实原因（指 `loop="none"`）。

## 问题 4：服务静默卡死 —— `POSTGRES_HOST=localhost` 让 psycopg async 挂住

### 现象
修好问题 3 后，启动**不再报错**，但服务停在下面这行之后**再无输出**（不报错、不超时）：

```
[API] embedding-service 就绪
        ← 卡在这里，永远等不到「Postgres checkpointer 就绪」
```

### 根因
`container.start()` 的次序是「DB 连通性校验（asyncpg）→ MinIO 建桶 → embedding 探测 →
**checkpointer（psycopg）**」。前几步都过了，说明 asyncpg 连 `localhost` 正常；
但 **psycopg async 的 `AsyncConnection.connect("...@localhost:5432/...")` 会静默卡死**。

隔离实验（同一 DSN，只换主机写法）：

| 组合 | 结果 |
| --- | --- |
| Selector + `127.0.0.1` | ✅ connect **0.04s** |
| Selector + `localhost` | ❌ 静默挂住（>120s 无返回） |
| Proactor + `localhost` | ❌ 快速报 InterfaceError |

即 **asyncpg 容忍 `localhost`，psycopg async 不容忍**；所以只有 checkpointer 这一步中招。

### 解决
`.env` 里把 `POSTGRES_HOST` 改成 `127.0.0.1`（`REDIS_HOST` / `MINIO_ENDPOINT` 早已是
`127.0.0.1`——同一个坑，早先修过，这次是 POSTGRES 漏了）：

```diff
- POSTGRES_HOST=localhost
+ POSTGRES_HOST=127.0.0.1
```

### 验证（真跑，非推断）
起服务后：`GET /health` → 200；`GET /metrics` → 正常；日志中 `ProactorEventLoop` 出现 **0 次**、
无 Traceback，出现「Postgres checkpointer 就绪」。
